# 训练日志诊断：脚本使用与移植手册

> 本文件与 `analyze_training_log.py` 配套，**两个文件一起复制**到任意 RL 项目即可复用整套「日志 → 诊断」能力。
> 前提：目标项目的训练输出按本文件第 2 节的「格式契约」对齐（或轻微适配第 3 节的正则）。

---

## 1. 这套东西解决什么问题

RL 训练最难的不是「写算法」，而是**出了问题不知道从哪查**。训练不稳、覆盖率不达标、奖励曲线不对，通常有两个隐蔽根因：

1. **环境状态不可控**（起点/障碍物/目标/朝向有隐式随机性），导致两次跑出来结果天差地别，让人误以为是算法问题。
2. **奖励函数与真实行为错配**（该给的分没给、给错了对象、惩罚过重），但只有总奖励曲线，看不到「谁、哪一步、因为什么拿到了什么分」。

本工具用**一个脚本**把大日志全量读入、输出精简诊断报告，自动识别训练问题 + 奖励函数问题，并给解决方向。核心价值：**省 token（不用人读几 MB 日志）+ 自动溯源 + 跨项目通用**。

## 2. 格式契约（目标项目要对齐的行前缀）

脚本靠正则识别「行前缀」，不关心内容细节。目标项目的训练输出里，**只要有下面这些行（前缀对齐即可）**，脚本就能工作。带 ★ 的是强烈建议有的，其余可选。

| 行前缀 | 含义 | 必要性 |
|---|---|---|
| `EP \| ep: N \| R: X \| cov:Y% \| steps: N \| loss:X \| [curQ:X \|] td:X` | 每回合汇总（奖励/覆盖率/步数/loss/Q/TD） | ★ 必选（趋势主料）|
| `REWARD(每智能体每步均值) \| name:+v name:-v ...` | 奖励分量均值 | ★ 强烈建议（奖励诊断的核心）|
| `运行设备：xxx` | 设备 | 可选 |
| `环境配置一览` + `网格尺寸/智能体起始位置/目标点位置/固定障碍物坐标/初始朝向/覆盖率达成阈值` | 环境快照 | ★ 强烈建议（对比实验先对齐环境）|
| `TRAIN[|-XXX] \| ep: N \| loss:X \| curQ:X \| tgtQ:X \| ... \| eps:X \| td:X` | 训练指标 | 可选 |
| `回合：N \| 全局奖励：X \| 覆盖率：Y%` | 最优模型记录 | 可选 |
| `全局平均覆盖率：X%` / `成功率：X%` / `平均完成步数：X` | 测试汇总 | 可选 |
| `Started at ...` / `Results reported at ...` / `CPU time: ...` / `Max Memory: ...` | 资源/时间 | 可选（用于算墙钟/内存）|

**关键点**：奖励分量（`REWARD(...)` 行）不是可有可无——它是「诊断奖励函数是否错乱」的唯一入口。没有它，脚本只能看趋势，无法定位奖励函数问题。

### 奖励分量怎么来（核心！）

奖励必须**在环境 step 内、行为发生的同一时刻**拆成带名字的分量，随 `info` 回传，训练循环只累加、不重算。示意（伪代码，不绑定框架）：

```python
# 环境 step 内
reward_components = {}
if 覆盖新格:
    reward_components["new_cell_base"] = 0.2
if 覆盖高价值格:
    reward_components["high_value_bonus"] = 0.8
if 撞障碍:
    reward_components["inner_invalid_penalty"] = -0.15
# ... 每个分量都要有名字
info["agent_info"] = [{ "agent_idx": i, "reward_components": {...}, ... }]
```

训练循环每 N 回合汇总一次，打印成：
```
REWARD(每智能体每步均值) | new_cell_base:+0.030 repeat_penalty:-0.049 stagnation_penalty:-0.028 ...
```

这样脚本就能分析：哪个分量主导、负奖励是否过重、里程碑是否触达。

## 3. 移植步骤（到新项目）

1. **复制两个文件**：`analyze_training_log.py` + 本手册，放到新项目的 `utils/`（或任意目录）。
2. **对齐格式契约**：在训练循环里加「每回合汇总行」和「奖励分量行」，按第 2 节的格式。
3. **（如格式有差异）改正则**：脚本顶部 `# 解析正则` 区块集中了所有正则，只改那里，不动诊断逻辑。
4. **跑一次**：
   ```bash
   PYTHONIOENCODING=utf-8 python utils/analyze_training_log.py 输出文件1.log 输出文件2.log
   ```
5. **看诊断报告**：概览 / 环境 / 训练趋势 / 覆盖率 / 奖励分量 / 测试 / 资源 / 诊断结论。

## 4. 输出报告怎么读（诊断思维）

脚本输出分 8 块，读法如下：

1. **[概览]**：设备、总轮次、理论最大奖励——先确认「这是哪次实验」。
2. **[资源]**：墙钟、CPU 核时、峰值内存——判断训练成本是否异常（如内存 11GB vs 1.8GB，说明模型/回放池规模差异）。
3. **[环境]**：起点/障碍物/目标/朝向/阈值——**对比两个日志前，先看这里是否一致**，不一致则结果差异可能来自环境而非算法。
4. **[训练N回合]**：奖励/覆盖率/步数的 均值+头尾——一眼看收敛趋势。**头尾对比**是关键：尾>头=在进步，尾<头=退化。
5. **[指标]**：loss/curQ/tgtQ/eps/td 首尾——loss 是否下降、Q 是否收敛、eps 是否衰减到位。
6. **[覆盖提升]**：覆盖率提升次数 + 峰值——覆盖能力上限。
7. **[奖励分量 top]**：按绝对值排序的前几名——**奖励函数诊断的主料**，重点看：
   - 负奖励是否挤进前三（惩罚过重，抑制探索）；
   - milestone_* 是否全 0（里程碑奖励从未触达）；
   - 某分量是否一家独大（奖励结构单一）。
8. **[诊断]**：脚本自动给出的问题 + 解决方向。

### 诊断背后的「溯源三问」

每次看报告，脑子里过这三个问题：

1. **奖励和覆盖率匹配吗？** 训练覆盖率峰值 99%，但测试掉到 81% → 训练-测试漂移（探索策略/约束在测试时失效）。
2. **奖励和真实行为匹配吗？** 高覆盖率阶段正激励 < 负惩罚 → 攻坚期被惩罚淹没，学不会最后 10%。
3. **两个实验可对比吗？** 环境快照不一致 → 任何差异都可能是环境造成的，先对齐再归因。

## 6. 边界与留有余量

- 本文是**一种可行做法**，不是唯一解：日志可以是 stdout 文本（正则抽取），也可以是 JSONL（更稳）；逐步明细可以打 stdout，也可以写 `.npz`/tensorboard。
- 脚本只依赖标准库，无第三方依赖，可安全复制。
- 诊断规则是**启发式**（阈值在 `diagnose_training` / `diagnose_reward` 里，可调），给的是「方向」而非「确定结论」——最终定位仍需结合代码。
