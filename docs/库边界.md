# 库边界：`rlinfra/` 是库，`algos/` 是应用，箭头只能向下

> 一句话：**`rlinfra/` 不知道世界上有哪个算法；`algos/` 可以 import 库；两者都不依赖 `main.py` / `config.py`。**
> 这条边界不是靠自觉，是靠 `python utils/check_boundaries.py` 七项自动检查（每项 FAIL → 退出码 1）。

---

## 1. 三层职责

| 层 | 路径 | 装进包吗 | 允许依赖 | 职责 |
|---|---|---|---|---|
| **① 库（基座）** | `rlinfra/` | ✅ | **只有 Python 标准库** | 日志契约 / 产物路径 / 资源计量 / 链路注册表。与算法、与任务、与项目配置都无关 |
| **② 示例算法包** | `algos/<algo>/` | ✅ | `rlinfra` + numpy/torch（**可选依赖**） | 一条链路 = 一个包 = 固定六件套；环境里放领域知识 |
| **③ 应用层** | `main.py` · `config.py` · `utils/` · `scripts/` | ❌ | 任意 | 本项目怎么跑：CLI dispatch、唯一配置源、诊断/画图/提交脚本 |

**为什么应用层不进包**：`config.py` 里的 `MADQN_lr`、`obstacle_num` 是**这个任务**的参数，不是基础设施的参数；
把它打进包里，等于把「示例」固化进「库」—— 换项目时第一个要删的就是它。

## 2. 依赖规则（能被检查抓住的那种）

| 规则 | 检查编号 | 违反会怎样 |
|---|---|---|
| `rlinfra/` 只用标准库 | ② | 装基座就得拖 numpy/torch，库变成框架 |
| `rlinfra/` 里不出现 `algos` | ③ | 基座知道算法存在 → 无法删除/替换算法 |
| `algos/` → `rlinfra/` 单向 | ④ | `algos/*` import `main`/`config` → 算法绑死项目，复用要连 CLI 一起搬 |
| `algos/madqn/madqn_envs.py` 不 import `config` | ⑤ | 环境拿不到「鸭子类型的 cfg」→ 换任务必须同时改 config 结构 |
| 注册表显式工厂 + 懒加载 | ⑥ | 退回「类重绑定」式隐式切换 → import 成功、跑错链路（UAV 项目真实事故） |
| `import rlinfra` 在任意 cwd 成立 | ⑦（`--installed`） | 只能 `cd` 到仓库根才能 import，等于没装 |

```powershell
python utils/check_boundaries.py              # ①–⑥（仓库内自检）
pip install -e ".[madqn]"
python utils/check_boundaries.py --installed  # 再加 ⑦（跨目录 import）
```

## 3. 包清单（`pyproject.toml`）

```toml
dependencies = []                                            # 基座零第三方依赖
[project.optional-dependencies]
madqn = ["numpy>=1.24", "torch>=2.0", "matplotlib>=3.6"]     # 示例链路才需要
plots = ["numpy>=1.24", "matplotlib>=3.6"]                   # 只跑报告/画图
[tool.setuptools]
packages = ["rlinfra", "algos", "algos.madqn"]               # 应用层不装
```

⇒ `pip install -e .` 之后：`import rlinfra` ✅、`import algos` ✅、`import algos.madqn` 需要 `[madqn]` extra。
`import config` / `import main` **不在包里** —— 它们是本项目的应用层，跑它们请 `cd` 到仓库根。

## 4. 加一条新链路（唯一正确的做法）

1. `cp -r algos/madqn algos/<新名>`，所有文件改前缀（`madqn_*` → `<新名>_*`）；
2. 在 `rlinfra/registry.py` **加一行** `register(AlgoSpec(chain="<新名>", package="algos.<新名>", ...))`；
3. `config.py` 的 `test_mode` 改成新链路名（或 `python main.py --test-mode <新名>`）；
4. `python utils/check_boundaries.py` 应仍然全绿；`python utils/smoke_test.py` 9 项应仍然全绿；
5. **禁止**用「给 `MADroneSearchEnv` 重新赋值成另一个类」的方式切换链路 —— 那正是本仓库刻意不用隐式注入的原因。

## 5. 已知妥协（诚实记录）

- **`runs_root` 默认是相对路径**（`RunPaths.runs_root = "runs"`）：产物目录跟随 cwd。装成库之后被别的程序调用时，
  要么传绝对 `runs_root`，要么在项目根下运行。**没有**改成「跟随包路径」是刻意的 —— 产物不该写进 site-packages。
- **`scripts/` 里写死了高算平台的绝对路径**（`/storage/public/home/__HPC_ACCOUNT__/RL_infra`）：这是**应用层脚本**，不是库；
  换机要改脚本，不需要改包。
- **只有一个算法包，还没有共享基类**：现在 `algos/madqn/` 是复制模板。抽基类的时机是**出现第二个包之后**，
  不是现在（提前抽象会把「六件套」锁死在错误的抽象上）。
- **`algos/madqn/madqn_trainer.py` 依赖 `rlinfra` 的三件（logger/metrics/paths）**：这是合法的向下依赖，
  但也意味着换掉日志契约会同时动到算法包 —— 代价登记在 `docs/架构决策.md`。

## 7. 参数改名映射（2026-10-17 #8：`MADQN_*` → `COMMON_*`）

**为什么改**：这批参数是**两条链路共用**的（DQN 族通用），但原先顶着 `MADQN_` 前缀 —— 名字宣布了一个虚假的归属。
迁移演练把追逃链路复制出来后，`pursuit_envs.py` 里出现 `cfg.MADQN_patch`，这个矛盾才暴露。

| 旧名（`cfg.` 后） | 新名 | 取值 |
|---|---|---|
| `MADQN_patch` | `COMMON_patch` | 2 |
| `MADQN_hidden_dim` | `COMMON_hidden_dim` | 128 |
| `MADQN_lr` | `COMMON_lr` | 5e-4 |
| `MADQN_gamma` | `COMMON_gamma` | 0.95 |
| `MADQN_batch_size` | `COMMON_batch_size` | 128 |
| `MADQN_buffer_size` | `COMMON_buffer_size` | 50000 |
| `MADQN_min_buffer` | `COMMON_min_buffer` | 1000 |
| `MADQN_learn_per_episode` | `COMMON_learn_per_episode` | 8 |
| `MADQN_target_update` | `COMMON_target_update` | 200 |
| `MADQN_eval_interval` | `COMMON_eval_interval` | 25 |
| `MADQN_eps_start` | `COMMON_eps_start` | 1.0 |
| `MADQN_eps_end` | `COMMON_eps_end` | 0.05 |
| `MADQN_random_episodes` | `COMMON_random_episodes` | 10 |

> **`MADQN_best_metric` 不改**：它确实只属于覆盖链路（追逃用 `PURSUIT_best_metric`）。

**取 值 逐 字 不 变**（改完核对过）：`obs_dim = 54`、`eps_decay_episodes = 230`、`n_actions = 9`，
`Config().to_dict()` 的键数 53 → 53、**没有任何值不同**（只是键名换了）。
⇒ 历史 run 的日志、checkpoint、`eval.json` 全部仍可读；不可复现的只有「用旧参数名写的外部脚本」。

**影响面**：12 个文件 / 168 行（机械改名）· CLI 的 `--lr` / `--batch-size` 仍然可用（`dest` 与 `metavar` 同步改了）·
`COMMON_patch` 仍是 `obs_dim` 的唯一派生源（`_derive()` 未改语义）。

**判定口径**：这是**重命名**，不是**重构** —— 它解决的是"名字骗人"，不是"参数放错地方"。
真正的结构性问题（哪些参数该进基座、哪些该进链路包）依然没解，见 §5 第 3 条。
